## 1. 目标与非目标

**问题**：后端编译目标为 Java 17、Spring Boot 3.3.5，没有启用虚拟线程。后续阶段需要 Boot 3.5（Spring AI 1.1.x 面向 Boot 3.5）和 Java 21。

| | 实施前 | 实施后 |
| --- | --- | --- |
| 编译目标 | 17 | 21 |
| Boot | 3.3.5 | 3.5.16（Hibernate 6.6.53.Final，Flyway 11.7.2，Lombok 1.18.46，mysql-connector-j 9.7.0，均由 BOM 管理）**[源码]** |
| springdoc | 2.6.0 | 2.8.17（其 parent 为 `spring-boot-starter-parent:3.5.13`）**[源码]** |
| 线程 | 平台线程 | `spring.threads.virtual.enabled=${VIRTUAL_THREADS:true}` |
| 连接池 | 默认 10 | `${DB_POOL_SIZE:20}` |
| 镜像 | `maven:3.9-eclipse-temurin-17` / `eclipse-temurin:17-jre` | `maven:3.9.11-eclipse-temurin-21-noble` / `eclipse-temurin:21.0.12.1_1-jre-noble` |

**JDK 运行时的维护状态**：

- Temurin 21 是 LTS 版本。
- `21.0.12.1_1` 是 2026-10-03 时 Docker Hub 上 21 线最新的 jre-noble 标签 **[源码]**。旧的 `21.0.8_9` 标签虽然仍然存在，但已落后 4 个季度补丁，**不得使用**。
- 执行 P1 时要再次查询：如果出现更新的 `21.0.x` 补丁标签，改用最新的，并在 PR 里记录。

**非目标**：任何业务逻辑、API、Redis key、schema 修改（除非 §6.4 的兼容迁移确实需要）；不拆模块；不引入 Kafka。

## 6. 实现契约

### 6.1 依赖核对

```bash
cd "$REPO/backend"
./mvnw -B -q help:effective-pom -Doutput="$P1_TMP/effective-pom.xml"
./mvnw -B -q dependency:list -DincludeScope=runtime -DoutputFile="$P1_TMP/deps.txt"
grep -E 'hibernate-core:jar:6\.6\.53\.Final|flyway-core:jar:11\.7\.2|flyway-mysql:jar:11\.7\.2|springdoc-openapi-starter-webmvc-ui:jar:2\.8\.17|mysql-connector-j:jar:9\.7\.0' "$P1_TMP/deps.txt" | wc -l   # 期望 5
grep -A1 '<artifactId>lombok</artifactId>' "$P1_TMP/effective-pom.xml" | grep -c '1.18.46'                                                                  # 期望 ≥1
```

结果写入 `scripts/db/evidence/p1/effective-versions.txt`。

### 6.2 `application.yml`

```yaml
spring:
  threads:
    virtual:
      enabled: ${VIRTUAL_THREADS:true}
  datasource:
    hikari:
      maximum-pool-size: ${DB_POOL_SIZE:20}
```

虚拟线程开启后，Tomcat 请求线程、`@Scheduled`（`reconcileEvents`、`SeckillStreamConsumer.drain`）和 `@Async` 都会改为在虚拟线程上执行 **[源码：Boot 3.2+ 文档行为]**。`SeckillStreamConsumer` 的语义不变。

### 6.3 `backend/Dockerfile`

```dockerfile
FROM maven:3.9.11-eclipse-temurin-21-noble AS build
WORKDIR /app
COPY pom.xml .
RUN mvn -B -q -e dependency:go-offline
COPY src ./src
RUN mvn -B -q -DskipTests package

FROM eclipse-temurin:21.0.12.1_1-jre-noble
WORKDIR /app
COPY --from=build /app/target/ecommerce-0.0.1-SNAPSHOT.jar app.jar
EXPOSE 8080
ENV JAVA_OPTS="-XX:MaxRAMPercentage=75"
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]
```

（构建阶段用镜像自带的 Maven 3.9.11，与 Wrapper 版本一致；这样 Docker 构建不依赖仓库里 Wrapper 的脚本。）

### 6.4 schema 不兼容时的处理

- 判定方法：P1 jar 在空库上启动失败、在 P0 基线化过的旧库上启动失败，或者 Hibernate 报 `Schema-validation:`。
- 处理方式：**不得修改 V1**。新增 `V1_1__p1_hibernate66_compat.sql`（Flyway 把它识别为版本 1.1，位于 V1 与 P2 的 V2 之间），只写最小的 `ALTER`，并在文件头注释写明原因和对应的 Hibernate 报错。
- 验证：
  - 空库：执行 V1 + V1_1 后，`validate` 通过；
  - 旧库：从 BASELINE(1) 执行到 V1_1 后，`validate` 通过；
  - 两个库的指纹一致。
- 如果需要修改的是数据而不只是结构，停止并请人工决策。

### 6.5 升级路径脚本 `scripts/p1/upgrade_path_check.sh`

1. 用 P0 的 `lib.sh` 启动临时 MySQL 和 Redis。
2. 用 `git worktree` 检出 `v0.4.2-baseline` 并构建；再检出 `P0_COMMIT` 并构建，得到两个 jar。`P0_COMMIT` 默认取 `git merge-base HEAD origin/main`，也就是 P1 分支的起点，即已经合并了 P0 的 main。
3. 在库 `ftsm_p1_legacy` 上，依次用基线 jar（开启种子数据）、P0 jar、P1 jar 启动，每次都 `wait_http` 到健康后停止。
4. 在库 `ftsm_p1_fresh` 上只用 P1 jar 启动。
5. 执行 `compare_schemas.sh ftsm_p1_fresh ftsm_p1_legacy`，输出写到 `scripts/db/evidence/p1/`。
6. 任一步失败，脚本以该步骤的退出码退出，并打印对应日志的最后 80 行。

## 10. 升级、重跑与恢复

- **已有数据**：Flyway 从 10.10 升级到 11.7.2 后会继续使用已有的 `flyway_schema_history`，这一点由 A5 验证。生产环境升级前，先在数据库副本上运行 `upgrade_path_check.sh`。
- **重跑**：脚本每次都会重建 `ftsm_p1_*` 临时库；compose 验收使用独立的项目名。
- **恢复**：回退代码即可回到 3.3.5。如果加了 V1_1，回退前需要手工撤销 V1_1 的结构变更，并删除 `flyway_schema_history` 里 1.1 那一行。**不支持自动降级**。
- **清理范围**：只清理 `ftsm-p1-acc` 项目、带 `ftsm.phase=p0` label 的临时容器，以及 `$P1_TMP`。
