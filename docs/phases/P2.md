> 全局约定见 [`../CHANGE_SPEC.md`](../CHANGE_SPEC.md) §0。证据标记含义同 P0：**[实验]** / **[源码]** / **[未验证]**。

## 1. 目标与非目标

**问题**：

- 现有秒杀链路是 Lua 扣减后 `XADD` 到 Redis Stream，由消费者落单。两次调用不是原子的，而且 Redis 只有 RDB 快照，重启可能丢消息。
- 热路径每次请求都 `findById` 查一次 MySQL。
- 普通 B2C / C2C 下单是“读出 → 修改 → 保存”，没有并发保护，会超卖。

| | 实施前 | 实施后 |
| --- | --- | --- |
| 购买意图持久化 | Redis Stream（RDB） | MySQL `order_outbox`，写入成功后才返回 202 |
| 落单 | `SeckillStreamConsumer`，每 500 ms 轮询 | Kafka `seckill.orders` → `SeckillOrderListener`，唯一键幂等 |
| 拒绝时的状态码 | 200 + `result` | 409 + `result`（body 结构不变）；outbox 写入失败时 503 `UNAVAILABLE` |
| 活动时间窗 | 每次请求查 MySQL | Caffeine 缓存，TTL 5 s |
| MySQL 侧的防线 | 无 | `seckill_events.sold_count < seckill_stock` 条件更新 |
| 普通商品 / C2C 下单 | 先读后写 | 在事务内做条件 `UPDATE` |
| Redis key | `seckill:stock:<id>` | `seckill:stock:{<id>}`（hash tag） |
| Redis 镜像 | `redis:7.4.6-alpine`（RDB） | `redis:8.10.2`，开启 AOF |

**非目标**：

- 不加 ShedLock，不做多副本支持（P6b）；
- 不做 sync 对照模式（P3）；
- 不修改前端组件。`SeckillCard.tsx` 本来就在 `catch` 里读取 `err.response.data.message`，所以本阶段只修改 `types/index.ts`；
- 不新增 Testcontainers（P6a）。

## 6. 实现契约

### 6.1 端到端事务边界与故障语义

| 步骤 | 位置 | 事务 | 成功后的状态 |
| --- | --- | --- | --- |
| T0 | `seckill_deduct.lua` | Redis 单脚本原子执行 | 库存减 1，用户加入 bought 集合 |
| T1 | `OutboxDao.insert`（JdbcTemplate，autocommit，**不在 Spring 事务中**） | 单行 INSERT | 购买意图已落盘 → 返回 202 |
| T2 | `OutboxPublisher.publishBatch`（`@Transactional`） | `SELECT … FOR UPDATE SKIP LOCKED` → Kafka send 并等待全部确认 → `markSent` → commit | 消息至少投递一次 |
| T3 | `SeckillOrderWriter.persist`（`@Transactional`） | INSERT order → `incrementSold` → `settle`（FAKE_WALLET，写为 PAID）→ commit | 订单已创建且为 PAID |
| T4 | Kafka offset 提交（`ack-mode: record`，监听方法正常返回后提交） | — | 消息已消费 |

| 故障场景 | 结果 | 处理 | 后果 |
| --- | --- | --- | --- |
| T0 之后、T1 之前进程崩溃 | 名额被扣，outbox 中没有记录 | 无法在线恢复；由对账发现 `redisSold > orderCount` | **少卖 1 件**，该用户被标记为已购，无法再买 |
| T1 抛出异常，并且确认没有写入（异常后用新连接执行 `existsByOrderId` 返回 false） | 补偿：执行 `seckill_rollback.lua` | 返回 503 `UNAVAILABLE` | 名额回到库存，用户可以重试 |
| T1 抛出异常，并且无法确认（`existsByOrderId` 本身也失败，例如数据库连接中断） | **不补偿**（无法确定是否已经提交） | 返回 503，ERROR 日志标记 `UNCERTAIN orderId=… userId=… eventId=…`；计数器 `seckill.outbox.uncertain` 加 1 | 如果实际已提交：稍后会正常落单（用户可以在“我的订单”里看到）；如果没有提交：少卖 1 件，由对账发现 |
| T1 抛出异常，但 `existsByOrderId` 返回 true（提交确认在网络上丢失） | 视为成功 | 返回 202 | 无 |
| 补偿脚本本身失败（Redis 不可用） | 名额没有还回去 | ERROR `COMPENSATION_FAILED`；计数器 `seckill.compensation.failed` 加 1；返回 503 | 少卖 1 件，由对账发现 |
| T2：send 成功，但 `markSent` 或 commit 失败，或者进程崩溃 | 这些行仍然是 NEW 状态 | 下一轮重新发送 | 消息重复，由 T3 的唯一键去重 |
| T2：任意一条 send 失败或超时（15 s） | 整批回滚 | 下一轮重试；WARN 日志 | 积压在 outbox 中，不丢消息 |
| T3：遇到唯一键冲突，并且 `existsByTrackingToken(orderId)` 为 true | 视为重复投递 | 正常返回，提交 offset | 无 |
| T3：遇到唯一键冲突，但这个 token 不存在（例如同一用户、同一活动，token 不同） | 异常情况 | **重新抛出** → 重试 3 次 → DLT | 需要人工排查 |
| T3：其他 `DataIntegrityViolationException`（NOT NULL、外键等） | 不是重复 | **重新抛出** → 重试 → DLT | 同上 |
| T3：`incrementSold == 0`（MySQL 侧防线触发） | 事务回滚 | `IllegalStateException` → 重试 → DLT | 防止超卖；需要人工排查 |
| T3 提交之后、T4 之前进程崩溃 | 消息会被重新投递 | 第一种唯一键冲突的情况 → 正常返回 | 无 |
| DLT 发布失败 | 恢复失败 | 记录不提交 offset，会被重新投递，一直重试到 DLT 可用为止；计数器 `seckill.dlt.publish.failed` 加 1，并打 ERROR 日志（**[未验证]**：Spring Kafka 3.3 在 recoverer 抛异常时会重新 seek 该记录，P6a 的 `DltPublishFailureIT` 负责证明）。期间该分区会阻塞 | 不会静默丢消息 |

**成立的保证**：

1. 不超卖：Redis Lua 是第一道防线，MySQL 的 `sold_count < seckill_stock` 是第二道。
2. 同一用户在同一活动里最多一张订单：唯一键 `uk_orders_buyer_seckill`。
3. 对返回过 202 的请求，订单最终一定会创建（只要 MySQL、Kafka 最终可用）。

**不成立、可能少卖的窗口**：上表中标注“少卖”的四种情况。全部会由 §6.8 的对账发现，不会自动修复。

### 6.2 消息体 `SeckillOrderMessage` v1

```java
public record SeckillOrderMessage(
        String orderId,        // UUID v4 string, == orders.tracking_token, NOT NULL
        Long userId,           // NOT NULL
        Long eventId,          // NOT NULL, Kafka key (String.valueOf)
        Long productId,        // NOT NULL
        BigDecimal price,      // NOT NULL, scale 2
        Instant acceptedAt) {} // NOT NULL
```

用 Boot 自动配置的 `ObjectMapper` 序列化为 JSON 字符串，写入 `order_outbox.payload`；Kafka 的 key 和 value 都用 `StringSerializer`。字段只允许新增，**不得**重命名或删除。

### 6.3 `V2__seckill_outbox.sql`

```sql
CREATE TABLE order_outbox (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  order_id    CHAR(36)    NOT NULL,
  user_id     BIGINT      NOT NULL,
  event_id    BIGINT      NOT NULL,
  payload     JSON        NOT NULL,
  status      TINYINT     NOT NULL DEFAULT 0,          -- 0 NEW, 1 SENT
  created_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  sent_at     DATETIME(3) NULL,
  UNIQUE KEY uk_outbox_order_id (order_id),
  KEY idx_outbox_status_id (status, id),
  KEY idx_outbox_event_status (event_id, status)
);

ALTER TABLE orders ADD COLUMN seckill_event_id BIGINT NULL;
UPDATE orders SET seckill_event_id = ref_id WHERE source_type = 'SECKILL';
ALTER TABLE orders ADD UNIQUE KEY uk_orders_buyer_seckill (buyer_id, seckill_event_id);

ALTER TABLE seckill_events
  ADD COLUMN sold_count INT NOT NULL DEFAULT 0,
  ADD COLUMN reconciled BIT(1) NOT NULL DEFAULT b'0';
UPDATE seckill_events e
   SET sold_count = (SELECT COUNT(*) FROM orders o WHERE o.source_type = 'SECKILL' AND o.ref_id = e.id);
UPDATE seckill_events SET reconciled = b'1' WHERE status = 'ENDED' OR end_time < CURRENT_TIMESTAMP(6);
UPDATE seckill_events SET stock_warmed = b'0' WHERE status = 'PENDING' AND start_time > CURRENT_TIMESTAMP(6);
```

- 历史秒杀订单的 `seckill_event_id` 由 `ref_id` 回填。
- 历史活动的 `sold_count` 按订单数计算。
- 已结束的活动直接标记为已对账，不会被新逻辑当作“待对账”。
- 未开始的活动会用新的 key 名重新预热。

**MySQL 的 DDL 不在事务中**：V2 执行到一半失败会留下部分变更。因此生产环境执行前必须先跑 §10.1 的预检（重复订单、进行中的活动等），并做好备份。

### 6.4 Redis

- `RedisKeys.seckillStock(id)` 返回 `"seckill:stock:{" + id + "}"`，`seckillBought(id)` 返回 `"seckill:bought:{" + id + "}"`。
- `seckill_deduct.lua` 的返回码保持不变：`1` 成功、`0` 售罄、`-1` 已购、`-2` 未预热。
- `seckill_rollback.lua`：

  ```lua
  -- KEYS[1]=stock KEYS[2]=bought ARGV[1]=userId ; idempotent: INCR only if SREM removed the user
  if redis.call('SREM', KEYS[2], ARGV[1]) == 1 then redis.call('INCR', KEYS[1]); return 1 end
  return 0
  ```

- 预热：`setIfAbsent(stockKey, seckillStock)`。返回 false 时打一行 INFO 日志，`stockWarmed` 仍然置为 true。
- `updateEvent`（只允许 PENDING 状态的活动）：先 `redis.delete(stockKey, boughtKey)`，再保存，然后 `eventCache.invalidate(id)`。
- `deleteEvent`：在原有删除逻辑之后再执行 `eventCache.invalidate(id)`。

### 6.6 `SeckillService.buy`

```java
public SeckillBuyResponse buy(Long userId, Long eventId) {
    var w = eventCache.get(eventId).orElse(null);
    if (w == null || !w.isActive(Instant.now())) return notActive();
    List<String> keys = List.of(RedisKeys.seckillStock(eventId), RedisKeys.seckillBought(eventId));
    long r = Optional.ofNullable(redis.execute(deductScript, keys, String.valueOf(userId))).orElse(-2L);
    if (r == 0) return soldOut();
    if (r == -1) return alreadyBought();
    if (r != 1) return notActive();
    String orderId = UUID.randomUUID().toString();
    String payload = json(new SeckillOrderMessage(orderId, userId, eventId, w.productId(), w.price(), Instant.now()));
    try {
        outboxDao.insert(orderId, userId, eventId, payload);
        return accepted(orderId);
    } catch (DataAccessException e) {
        Boolean exists = outboxDao.existsByOrderIdSafely(orderId);
        if (Boolean.TRUE.equals(exists)) return accepted(orderId);
        if (exists == null) { uncertain(orderId, userId, eventId, e); return unavailable(); }   // no compensation
        compensate(keys, userId, e);                                                         // logs+counts on failure
        return unavailable();
    }
}
```

`unavailable()` 返回的 message 为：“We could not confirm your order. Please check My Orders before trying again.”

### 6.7 Relay、Kafka 配置与消费者

- `OutboxRelay.run()`：`@Scheduled(fixedDelayString="${app.seckill.relay-interval-ms:100}")`。循环最多 20 次调用 `publisher.publishBatch()`，某一批返回值小于 `batchSize` 时提前结束；任何异常都捕获并打 WARN，不向外抛出。
- `OutboxPublisher.publishBatch()`（`@Transactional`，独立 bean，保证经过代理）：
  1. `lockBatch(batchSize)`；
  2. 逐条调用 `kafka.send(topic, String.valueOf(eventId), payload)`，收集返回的 future；
  3. `CompletableFuture.allOf(...).get(15, SECONDS)`；任何异常都包装为 `IllegalStateException` 抛出，整批回滚；
  4. `markSent(ids)`；
  5. 返回本批行数。
- `KafkaConfig`：

  ```java
  @Bean NewTopic seckillOrdersTopic()    { return TopicBuilder.name(topic).partitions(partitions).replicas(replicas).build(); }
  @Bean NewTopic seckillOrdersDltTopic() { return TopicBuilder.name(dltTopic).partitions(1).replicas(replicas).build(); }
  @Bean CommonErrorHandler kafkaErrorHandler(KafkaTemplate<String,String> t, MeterRegistry m) {
      var rec = new DeadLetterPublishingRecoverer(t, (r, ex) -> new TopicPartition(dltTopic, -1));
      rec.setFailIfSendResultIsError(true);
      rec.setWaitForSendResultTimeout(Duration.ofSeconds(10));
      var h = new DefaultErrorHandler(rec, new FixedBackOff(1_000L, 3));
      h.addNotRetryableExceptions(JsonProcessingException.class);
      h.setRetryListeners(new RetryListener() {
          public void failedDelivery(ConsumerRecord<?,?> r, Exception e, int attempt) {}
          public void recoveryFailed(ConsumerRecord<?,?> r, Exception original, Exception failure) {
              m.counter("seckill.dlt.publish.failed").increment();
              log.error("[SecKill] DLT publish failed for offset {}", r.offset(), failure);
          }
      });
      return h;
  }
  ```

  Boot 会把这个 `CommonErrorHandler` bean 自动装配到默认的 listener 容器工厂上 **[源码：Boot Kafka 自动配置]**。

- `SeckillOrderListener.onMessage(String payload)`：

  ```java

  } catch (DataIntegrityViolationException e) {
  ```

### 6.8 对账 `SeckillReconciler`

`@Scheduled(fixedDelay = 60_000)`。处理对象是 `status = ENDED`、`reconciled = false` 的活动。`grace = app.seckill.reconcile-grace`，默认 30 分钟。

1. `endTime + 2min > now`：跳过。
2. 计算 `pending = countPendingForEvent`、`published = countAllForEvent`、`orderCount = countBySeckillEventId`、`soldCount`。
3. 读取 `redisRemaining = GET seckill:stock:{id}`：
   - 抛异常：**不标记**，WARN “redis unavailable, will retry”，本轮结束；
   - key 不存在：`redisSold = null`；否则 `redisSold = seckillStock - redisRemaining`。
4. `caughtUp = (pending == 0 && orderCount == published)`。
5. 判定：
   - `caughtUp` 且所有非 null 的数都相等：标记，INFO。
   - `caughtUp` 但不一致：标记，WARN，打出全部数字，计数器 `seckill.reconcile.mismatch` 加 1；`redisSold > orderCount` 时写明“lost slots (undersell)”。
   - 未 `caughtUp`，且 `now < endTime + grace`：不标记，DEBUG，下一轮再查。
   - 未 `caughtUp`，且 `now ≥ endTime + grace`：标记，WARN “consumer backlog not drained within grace”，计数器 `seckill.reconcile.incomplete` 加 1。
   - `redisSold == null`（且已 `caughtUp` 或已过 grace）：标记，WARN “redis key missing”，计数器 `seckill.reconcile.incomplete` 加 1。
6. 标记的含义是“已给出最终结论”，不代表结果一致。

与 `OutboxJanitor` 的关系：Janitor 只删除 `reconciled = 1` 的活动的 SENT 行。因此只要对账还没完成，`published` 计数就一直准确。

## 10. 升级、重跑与恢复

### 10.1 生产切换清单（`scripts/p2/precheck_cutover.py`，只读，任何一项失败就以非 0 退出码退出）

1. 没有进行中或即将开始的活动：`SELECT COUNT(*) FROM seckill_events WHERE end_time >= NOW(6) AND start_time <= NOW(6) + INTERVAL 30 MINUTE` 必须为 0。
2. 旧 Stream 已经消费完：`XPENDING seckill:orders seckill-order-consumers` 的计数为 0，并且 `XINFO GROUPS seckill:orders` 的 `lag` 为 0。
3. Stream 里每一条消息都已落单：用 `XRANGE seckill:orders - +` 取出全部 token，逐一检查 `orders.tracking_token` 是否存在，缺失数必须为 0。
4. 没有重复的历史秒杀订单：`SELECT buyer_id, ref_id, COUNT(*) FROM orders WHERE source_type='SECKILL' GROUP BY 1,2 HAVING COUNT(*)>1` 必须返回 0 行。
5. 所有未结束的活动都满足 `sold_count(推算值) ≤ seckill_stock`。
6. 生成一份备份：`mysqldump --single-transaction ftsm_ecommerce > backup-<ts>.sql`。脚本只打印这条命令，由人执行。

预检通过后的切换步骤：

1. 停止 backend（这本身就是暂停流量：前端会显示错误，需要提前公告维护窗口）；
2. 部署 P2，启动时 Flyway 会执行 V2；
3. 确认 V2 的 success 为 1；
4. 执行 `RENAME seckill:orders seckill:orders:archive:<yyyyMMdd>` 归档旧 Stream（保留，不删除）；
5. 确认未开始的活动已经用新 key 名重新预热；
6. 恢复流量。

### 10.2 其他规则

- **重跑**：V2 只会执行一次（由 Flyway 保证）；验收在独立的 compose 项目中进行，可以 `down -v` 后重来。
- **V2 执行失败**：MySQL 的 DDL 不在事务中，可能留下部分变更。处理办法是用第 6 步的备份恢复数据库，然后回滚到 P1 的代码。**不支持**修改 V2 后再重新执行。
- **降级到 P1**：只能从备份恢复，不支持自动降级。
- **清理**：只针对 `ftsm-p2-acc` 项目和 `$P2_TMP`。
