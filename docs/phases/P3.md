## 1. 目标与非目标

**问题**：要回答“Outbox+Kafka 相比同步落单、相比旧版本，性能和可靠性如何”，需要三组可对照的配置，以及一套不会混用旧结果、不会把拒绝请求当作成功订单的测量方法。

| | 实施前 | 实施后 |
| --- | --- | --- |
| 对照模式 | 没有 | `app.seckill.mode=sync`：Lua 扣减成功后在请求线程里直接落单（只用于压测） |
| 测量指标 | 只有请求速率 | 三种吞吐：请求吞吐、业务接受吞吐、最终落库吞吐；外加 p50/p95/p99 和 `dropped_iterations` |
| 结果组织 | — | `loadtest/results/<config>/<RUN_ID>/`，每次运行带 `run.json`、`summary.json`、`verify.tsv`、`persist.tsv` |

**非目标**：
- 不改变默认行为。默认仍为 `async`，与 P2 完全一致。
- 不调优业务代码。
- 正式测量完成之前，不得在 README 或简历里写任何“性能提升”的结论。

## 6. 实现契约

### 6.1 sync 分支（在 Lua 返回 1 之后）

```java
if (mode == Mode.SYNC) {
    try {
        writer.persist(msg);                                   // T3 in the request thread; same transaction as P2
        return accepted(orderId);
    } catch (DataIntegrityViolationException e) {
        if (writer.existsByTrackingToken(orderId)) return accepted(orderId);   // cannot normally happen; defensive
        compensate(keys, userId, e);                           // constraint violation for a new token: give slot back
        return unavailable();
    } catch (RuntimeException e) {                             // includes commit failures and the MySQL stock guard
        Boolean exists = writer.existsByTrackingTokenSafely(orderId);
        if (Boolean.TRUE.equals(exists)) return accepted(orderId);
        if (exists == null) { uncertain(orderId, userId, eventId, e); return unavailable(); }   // no compensation
        compensate(keys, userId, e);
        return unavailable();
    }
}
```

- 补偿、uncertain 日志和计数器与 P2 共用同一组方法（`compensate`、`uncertain`）。
- sync 模式下**不写 outbox，也不发 Kafka**。
- 重复消息的概念不适用于 sync：同一请求只会调用一次 `persist`。
- 返回码与 P2 相同：202 / 409 / 503。

### 6.2 默认行为

`app.seckill.mode` 未设置时为 `ASYNC`，代码路径与 P2 完全一致。`SeckillServiceSyncModeTest` 中包含一个断言：默认构造时没有调用 `writer.persist`，而是调用了 `outboxDao.insert`。

### 6.3 指标定义（`summarize.py` 唯一认可的计算方式）

| 指标 | 定义 | 来源 |
| --- | --- | --- |
| 请求吞吐 `requestRps` | 稳定阶段的 `http_reqs` 计数 ÷ `STEADY_SECONDS` | `summary.json` 的 meta |
| 业务接受吞吐 `acceptedRps` | 稳定阶段 `result=ACCEPTED` 的计数 ÷ `STEADY_SECONDS` | 同上 |
| 最终落库吞吐 `persistedRps` | 该活动的订单数 ÷ (max(created_at) − min(created_at))，单位为秒 | `persist.tsv` |
| 落库延迟上界 `drainSeconds` | `drain.sh` 从开始到成功所用的秒数 | `run.json` |
| 延迟 | 稳定阶段 `http_req_duration` 的 p50 / p95 / p99 | `summary.json` |

`loadtest/persist.sql` 要兼容 A 配置，所以列名按版本二选一，由 run.sh 根据 `--drain` 模式选择 `ref_id` 或 `seckill_event_id`：

```sql
SELECT COUNT(*) AS orders,
       TIMESTAMPDIFF(MICROSECOND, MIN(created_at), MAX(created_at)) / 1e6 AS span_s
FROM orders WHERE source_type = 'SECKILL' AND <ref_id|seckill_event_id> = @event_id;
```

- 409 的快速拒绝**不计入**业务接受吞吐。
- 吞吐场景必须满足 `seckill_accept_rate{scenario:steady} ≥ 0.99`，否则说明库存设小了，这次运行无效。
- **一次运行有效**的条件：
  - k6 退出码为 0（包括 `dropped_iterations{steady}==0`、`UNPARSEABLE==0`、`accept_rate≥0.99`）；
  - drain 成功；
  - `verify.orders == meta.accepted`；
  - B 配置额外要求 `order_outbox` 中该活动的行数为 0。

## 7. 配置与运行

### 7.1 基准环境

- `loadtest/bench/infra_up.sh`：

  ```bash
  docker compose -p ftsm-p3-bench --env-file "$BENCH_ENV" up -d mysql redis kafka
  ```

  `$BENCH_ENV` 中定义端口 33306 / 36379 / 39092，以及 `DB_PASSWORD=bench`。然后对 mysql 和 kafka 各执行一次 `wait_cmd 180`。
- 后端在宿主机上以 JVM 进程运行，三种配置使用相同的 JDK 21 和相同的 JVM 参数 `-Xms2g -Xmx2g -XX:+UseG1GC`。
- 环境变量：`BACKEND_DB_PORT=33306`、`BACKEND_REDIS_PORT=36379`、`BACKEND_KAFKA=127.0.0.1:39092`（A 配置不需要 Kafka，设置了也不影响）。

### 7.2 `run_config.sh` 的流程（每次调用一个配置、一个场景）

1. A 配置在 `$BENCH_TMP/baseline` 构建 tag 对应的 jar（已有则复用）；B、C 配置在仓库根执行 `./mvnw -B -q -DskipTests package`（P4a 之前改为 `cd backend && ./mvnw …`）。
2. 每个配置使用独立的数据库：`ftsm_bench_a`、`ftsm_bench_b`、`ftsm_bench_c`。首次启动时会自动建库，并由 Flyway 执行迁移；A 配置由 Hibernate 建表。
3. 调用 `start_backend` 并 `wait_http` 180 s；失败时退出码 2。
4. 预热：执行一次 `run.sh --scenario throughput --rate 50 --ramp 5 --steady 10`，结果写入 `results/<config>/warmup/`，**不计入**汇总。
5. 调用 `run.sh` 执行正式运行，参数为 `--mysql compose:ftsm-p3-bench:$BENCH_ENV:ftsm_bench_<a|b|c> --redis compose:ftsm-p3-bench:$BENCH_ENV`；`run.sh` 内部依次完成 setup_event、k6、drain、verify、persist。
6. `stop_backend`。
7. 清理：先确认没有 k6 进程在运行（`pgrep -f 'k6 run'` 为空），并且 drain 已成功，然后才执行 `CONFIRM_RESET=yes loadtest/reset.sh`（只删除秒杀相关的 Redis key，以及 SECKILL 订单和 outbox 行）。**不允许**在消费过程中删除订单或裁剪 Stream。
8. 最终退出码 = `run.sh` 的退出码。

### 7.3 人工正式测量流程

1. 按 `ENVIRONMENT.md` 填写环境记录。
2. `infra_up.sh`。
3. 对 A、B、C，`RATE` 从 1000 开始，每档加 500：
   - 每档跑 3 次 `run_config.sh <cfg> throughput --rate R --ramp 60 --steady 120`；
   - 出现以下任一情况就停止加档：任一次运行无效，或 p99 ≥ 1000 ms，或错误率 ≥ 1%；
   - 记录最后一个三次都有效的档位，作为“可持续速率”。
4. 争抢场景：每个配置跑 3 次，`--stock 100 --buyers 5000 --vus 1000`。
5. `python3 loadtest/summarize.py --dir loadtest/results --configs A,B,C --format markdown > loadtest/results/SUMMARY.md`。
6. 把汇总表复制到 README 的 Performance 一节，并附上环境记录。不足 3 次有效运行的配置，在表里写“未完成”。
7. `infra_down.sh`：`down -v`，只针对 `ftsm-p3-bench` 项目。

## 10. 升级、重跑与恢复

- sync 模式只是一个配置项，不涉及数据迁移。
- 重跑：每次运行都新建一个 run 目录，从不覆盖；`infra_down.sh` 之后可以从头再来。
- 恢复：某次运行失败时，它的目录保留，但会被 `summarize.py` 标为 invalid；不需要手工删除。
- 清理范围：只针对 `ftsm-p3-bench` 项目、`$BENCH_TMP`，以及 `ftsm_bench_*` 这些库（它们都在 bench 项目自己的卷里）。
